# Docker Standards — Catraca

This document describes the Docker, Compose, Makefile and ignore conventions we use across Catraca projects. It exists to give context to anyone joining the team (and to the community, if you want to adopt the same pattern) and to justify **why** each decision exists, not only what it does.

> 🇧🇷 Versão em português: [README_PT-BR.md](./README_PT-BR.md)

## Example stack used throughout the document

The whole practical part uses a generic four-layer stack:

| Service     | Technology   | Role                                                  | Public exposure |
|-------------|--------------|-------------------------------------------------------|-----------------|
| `frontend`  | Next.js      | Browser UI (SSR + client)                             | Yes (HTTPS)     |
| `bff`       | NestJS       | Backend-for-frontend: aggregates/adapts the `backend` | Yes (HTTPS)     |
| `backend`   | Go           | Domain API (business rules, persistence)              | **No** in prod  |
| `database`  | MongoDB      | `backend` persistence                                 | **No**, ever    |

On top of that, a **shared external network** named `catraca` connects every project in this repo (and other repos in the org). In production, only `frontend` and `bff` are exposed to the outside world; `backend` and `database` are invisible. In dev, the override exposes the `backend` port for Postman/debug.

### Why is there a BFF between the frontend and the backend?

The BFF (Backend-for-frontend) is a facade layer: it receives browser requests over HTTPS and talks to the `backend` over Docker's internal network. In production, the `backend` has no `ports:` declared. Nothing outside can reach it, and the BFF is the only public frontier between the outside world and the domain. Other benefits (composing responses for the frontend, centralizing auth and rate limiting) come along for free, but the primary motivation in our pattern is this: **shield the backend behind one extra layer**.

> From here on: "BFF" is the NestJS layer that exposes HTTPS to the world, "backend" is the internal Go API, "database" is Mongo. Pattern originally described by [Phil Calçado](https://philcalcado.com/2015/09/18/the_back_end_for_front_end_pattern_bff.html) and [Sam Newman](https://samnewman.io/patterns/architectural/bff/).

## 1. File architecture overview

Every project follows the same minimal structure:

```
project/
├── .docker/
│   ├── build/
│   │   └── Dockerfile                  # single Dockerfile, multi-stage
│   ├── data/                           # local volumes (ignored by git)
│   └── .gitignore                      # ignores `data/` inside .docker itself
├── .dockerignore                       # trims size and secrets from the build context
├── .gitignore
├── Makefile                            # bootstrap + daily shortcuts
├── .env.sample                         # versioned env template
├── .env                                # local copy (gitignored), generated by make
├── docker-compose.yml                  # base stack that locally mirrors the prod environment
├── docker-compose.override.yml.example # versioned override template
└── docker-compose.override.yml         # local copy of the default (gitignored)
```

This repetition is intentional: when switching between repositories, developers find the same touchpoints in the same places.

---

## 2. The `.docker/` folder

### Why it exists

The `.docker/` folder groups **everything that belongs to Docker but not to the application code**:

- `build/Dockerfile` — build recipe.
- `data/` — local bind mounts (database, redis, etc.).
- Optional subfolders for stateful services (`grafana/`, `redis_data/`, …) when Compose needs to mount them.

### Benefits

1. **Clean project root.** No 4-5 `Dockerfile.*`, `docker-entrypoint.sh`, scattered configs polluting `ls`.
2. **Single ignore scope.** Because all Docker stuff lives under `.docker/`, a single line in `.dockerignore` (`.docker`) keeps the build/data/provisioning directory out of the build context, so it never bloats the image.
3. **Versioned files and volatile data coexist.** `.docker/build/Dockerfile` goes into git; `.docker/data/` stays out via an internal `.docker/.gitignore` (one line: `data`). This avoids polluting the root `.gitignore` with low-level rules.
4. **Predictable path for Compose.** Every `docker-compose.override.yml` points to `dockerfile: .docker/build/Dockerfile`. No ambiguity about "which Dockerfile do I use?".

## 3. Multi-stage Dockerfile

Before talking about Compose, we need the right Dockerfile. Every project uses a **multi-stage** Dockerfile to serve the same file in dev and in production. Without that, you end up with `Dockerfile.dev` and `Dockerfile.prod` drifting apart over time.

A "stage" is a section of the Dockerfile started by `FROM ... AS <name>`. Each stage can copy files from earlier stages via `COPY --from=<stage>`. In the end, only the last stage becomes the default image; the intermediate ones serve as build cache sources.

### Node example (Next.js frontend / NestJS bff)

```dockerfile
FROM node:22-alpine AS base

# 1. deps — only installs node_modules
FROM base AS deps
RUN apk add --no-cache libc6-compat
WORKDIR /app
COPY package.json package-lock.json* ./
RUN npm ci

# 2. dev — hot reload (start:dev in NestJS, next dev in Next.js)
FROM base AS dev
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
EXPOSE 3000
CMD ["npm", "run", "start:dev"]

# 3. builder — produces the production build
FROM base AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npm run build

# 4. runner — minimal final image, non-root user
FROM base AS runner
WORKDIR /app
ENV NODE_ENV=production
RUN addgroup --system --gid 1001 nodejs && adduser --system --uid 1001 app
COPY --from=builder --chown=app:nodejs /app/dist ./dist
COPY --from=builder --chown=app:nodejs /app/node_modules ./node_modules
COPY --from=builder --chown=app:nodejs /app/package.json ./
USER app
EXPOSE 3000
CMD ["node", "dist/main.js"]
```

> In Next.js, swap the `runner` to use `standalone output` (a Next.js feature that bundles only what's strictly needed at runtime): `COPY /app/.next/standalone ./` + `COPY /app/.next/static ./.next/static`. Produces an even smaller image, with no `node_modules` at runtime.

### Go example (backend)

```dockerfile
FROM golang:1.25-alpine AS dev
RUN go install github.com/air-verse/air@latest
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
CMD ["air", "-c", ".air.toml"]

FROM dev AS build
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-w -s" -o /app/build/server ./cmd/server

FROM scratch
# CA certificates: required for outbound HTTPS calls
COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
# tzdata: required if the app uses time.LoadLocation ("America/Sao_Paulo", etc.)
COPY --from=build /usr/share/zoneinfo /usr/share/zoneinfo
# /etc/passwd: required if running as a non-root USER
COPY --from=build /etc/passwd /etc/passwd
COPY --from=build /app/build/server /server
EXPOSE 8080
ENTRYPOINT ["/server"]
```

> **Modern alternative:** instead of assembling `scratch` by hand, consider `gcr.io/distroless/static-debian12:nonroot` (Google) or `cgr.dev/chainguard/static` (Chainguard). Both ship with `ca-certificates`, `tzdata`, a non-root user, and receive security updates, without you having to remember to copy three files from the build stage. `scratch` is still valid when every megabyte matters or when "zero layers beyond your binary" is a requirement.

### Multi-stage advantages

1. **One Dockerfile, multiple targets.**
   - `target: dev` in the Compose override → runs hot reload.
   - No `target` in the main compose → builds up to the last stage (`runner` or `scratch`) and uses the lean production image.
   This eliminates the `Dockerfile.dev` + `Dockerfile.prod` duplication.

2. **Cache reused across stages.** The `deps` stage only runs `npm ci` (or `go mod download`) when `package.json`/`package-lock.json` (or `go.mod`/`go.sum`) change. Code changes (`COPY . .` in `builder`) don't invalidate the dependency layer.

3. **Lean final image.**
   - Go backend ends with `FROM scratch` (only the static binary + CA certificates). Result: image in the **tens of MB** range, no shell, no package manager, no system-package CVEs.
   - Next.js frontend with `standalone output` copies only what's strictly necessary, no `node_modules` at runtime.

4. **Security by construction.**
   - Non-root user at runtime.
   - No `npm`/`apk`/`bash` in the final image → smaller attack surface.
   - `CGO_ENABLED=0` in Go → static binary with no libc dependencies, runs on any minimal base.

5. **Multiple binaries from a single image.** In Go projects with several `cmd/*` (e.g. `server`, `worker`, `scheduler`), just iterate inside the `build` stage and produce all of them. Then `docker-compose.yml` runs **the same image with a different `command`** (N services, one build).

## 4. Docker networks

With the Dockerfile sorted, the next fundamental block is how containers connect.

### Two networks, three exposure zones

Each project declares **two networks** in compose, and combining them with the presence or absence of `ports:` produces three visibility zones:

| Zone              | Who's there                              | How it's reached                          |
|-------------------|------------------------------------------|--------------------------------------------|
| Public (host)     | Services with `ports:` declared          | `localhost:PORT` in the browser            |
| `catraca` (across projects) | Services listed in `networks: [catraca]` | Other catraca containers resolve them by service name |
| `internal` (project-scoped) | Everything in the project's compose      | Only the project's own containers see each other |

Databases live **only in `internal`**. BFF and frontend live in `internal` + `catraca`. The `backend` is also in both, but without `ports:` in production.

### Why two networks instead of one

- **Isolation.** This project's `database` doesn't need to be (and shouldn't be) visible to other org projects. By keeping it in `internal` only, it's unreachable from other repos even when they're all running.
- **Smaller attack surface.** Containers that don't export a public service (database, cache, worker) stay on the internal network only. Only apps that need to talk to other projects join `catraca`.
- **Order-independent startup.** Because `catraca` is `external`, you start projects in any order: when the second one comes up, it already sees the first via Docker's internal DNS.
- **Free cross-project DNS.** Inside `catraca`, any service resolves by name (`bff`, `backend`, `gateway`…), no static IPs, `/etc/hosts` editing, or service discovery config required. See section 5 for how this works in detail.

### Declaration in compose

```yaml
networks:
  internal:                        # Compose prefixes with COMPOSE_PROJECT_NAME → becomes "<project>_internal"
  catraca:
    external: true
    name: catraca                  # `name:` disables the prefix and uses the literal name in the daemon
```

Each service picks the networks it joins:

```yaml
services:
  frontend:
    networks: [catraca]            # public + catraca only; doesn't talk to db directly
  bff:
    networks: [internal, catraca]  # talks to internal backend + other projects
  backend:
    networks: [internal, catraca]  # internal for database, catraca to be called
  database:
    networks: [internal]           # NEVER on catraca: database is project-private
```

### Idempotent external network creation

The external network has to exist **before** any `docker compose up`, otherwise Compose fails with `network catraca declared as external, but could not be found`. The project's Makefile handles this with an idempotent target:

```makefile
EXTERNAL_NETWORK := catraca

.PHONY: network
network: ## Create the external network `catraca` if it doesn't already exist
	@if docker network inspect $(EXTERNAL_NETWORK) >/dev/null 2>&1; then \
		echo "✓ Network '$(EXTERNAL_NETWORK)' already exists"; \
	else \
		echo "→ Creating network '$(EXTERNAL_NETWORK)'..."; \
		docker network create --driver bridge $(EXTERNAL_NETWORK); \
		echo "✓ Network '$(EXTERNAL_NETWORK)' created"; \
	fi
```

Details:

- **Idempotent.** `docker network inspect` returns 0 if the network exists, ≠0 otherwise. `make` only creates it when needed.
- **Explicit `--driver bridge`.** It's the default, but the explicit form makes intent clear (no `overlay`/`macvlan`). _Note: `--attachable` only matters for `overlay` networks in Swarm mode; on a single-host `bridge` it's a no-op._
- **Transitive dependency.** The `setup`, `up`, and `prod-like` targets all list `network` as a prerequisite, so the developer never forgets to create it.
- **Not removed by `clean`.** `docker compose down -v` only tears down project resources; the external network stays up because other projects depend on it. To remove it, use `make network-rm` (only succeeds if no container is connected).

### Who lives in which zone

| Service     | Host port            | `catraca` network | `internal` network |
|-------------|----------------------|-------------------|--------------------|
| `frontend`  | ✓ `3001:3000`         | ✓                 | ✗                  |
| `bff`       | ✓ `3000:3000`         | ✓                 | ✓                  |
| `backend`   | ✗ (only in dev override)| ✓               | ✓                  |
| `database`  | ✗                     | ✗                 | ✓                  |

Reading the table: `frontend` is reachable by the browser and by other catraca projects, but it can't see `database`. The `database` is only seen by `backend` (because both sit on `internal`); nobody from outside can reach it, not even another project on the same machine.

### How a request traverses everything

```
browser
   │  HTTPS localhost:3000
   ▼
[ bff ]  ──► http://backend:8080   (via catraca or internal — both resolve)
   ▲
   │
[ backend ]  ──► mongodb://database:27017   (via internal)
                      ▲
                      │
                [ database ]
```

The `frontend` does the same trip for public navigation: browser → `localhost:3001` → frontend → `http://bff:3000` (via catraca) → backend → database.

### Why this matters

1. **Plug-and-play across repos.** For `bff` to call a service from another project, you don't change configuration, you don't create an IP. Just make sure both are on `catraca` and use `http://service-name:port`.
2. **Defense in depth.** Database remains invisible even if another app on the same machine is compromised. Backend remains invisible unless the BFF leaks it.
3. **Dev/prod parity.** In production, you can swap `catraca` for an overlay/Swarm/Kubernetes service mesh without changing the compose structure; only how the network is created changes.
4. **Safe onboarding.** First-time cloners don't have to remember `docker network create catraca`. `make setup` (and `make up`) handles it.

## 5. Docker's internal DNS: how services see each other

Networks are only useful because they come with **automatic DNS**. When a container needs to talk to another, it uses a *hostname*, not an IP. That hostname is the **service name in `docker-compose.yml`**.

### The service name is the hostname

Whenever you declare:

```yaml
services:
  backend:
    ...
```

Docker automatically creates a DNS entry for `backend` resolvable by any container on the same network. No `/etc/hosts` to edit, no DNS configuration to do. Docker maintains an embedded resolver (listening on `127.0.0.11` over TCP+UDP inside every container) that answers queries by service name.

> This embedded DNS only exists in **user-defined networks** (any network you create via compose or `docker network create`). The original default `bridge` network has no name resolution. Yet another reason to always declare your own networks.

So the BFF calling the backend is literally:

```
http://backend:8080
```

The `8080` there is the **internal** port of the backend container (the one from `EXPOSE 8080` in the Dockerfile), not the host port. This holds even if the backend has no `ports:` declared: the internal port always exists, only host publishing is optional.

### Why `localhost` does NOT work between containers

Common onboarding mistake: setting `BACKEND_URL=http://localhost:8080` on the BFF. Doesn't work, because:

- `localhost` inside a container resolves to the network interface visible only to itself (`127.0.0.1` of that specific container).
- The backend isn't running inside the BFF's container; it's in another container, with its own network interface and its own `localhost`.
- The `8080` you see at `localhost:8080` on **your host (laptop)** only exists because you declared `ports: "8080:8080"` in compose; that's a bridge from the host to the container, not something other containers use.

Summary of who talks to whom and how:

| Source                                   | How it reaches `backend`              |
|------------------------------------------|---------------------------------------|
| Another container on the **same network**| `http://backend:8080` (Docker DNS)    |
| Your browser / Postman on the **host**   | `http://localhost:8080` (only works if the service publishes `ports:`) |
| Container NOT on the same network        | Can't reach it (even if running side by side) |

### Internal port vs published port

In a line like:

```yaml
ports:
  - "${BFF_PORT:-3000}:3000"
```

- The number on the **left** = port on the HOST.
- The number on the **right** = port INSIDE the container.

Other containers always use the **internal** port (right). Only the host (browser, Postman, `curl localhost`) uses the external port (left).

Practical example: if you want two projects on the same host and both BFFs listen on 3000, just change the left side in one of their overrides:

```yaml
bff:
  ports:
    - "3100:3000"   # host:container — only the host port changes
```

The BFF still listens on 3000 internally. Other containers keep calling `http://bff:3000` without changing anything. Only your browser now needs `http://localhost:3100`.

### Networks define visibility

DNS only works within a shared network. If `bff` is on `[internal, catraca]` and `backend` is also on `[internal, catraca]`, they see each other through either network. If you forget to put the backend on `catraca`, projects from other repos can't reach it, even when running on the same Docker daemon.

Resolution rules of thumb:

- Same network → resolves directly by service name.
- Different networks (same daemon) → does not resolve.
- `external: true` network (`catraca`) → all projects joining it share resolution, as if they were a single stack.

### Talking to something OUTSIDE Docker: `host.docker.internal`

Sometimes a container needs to reach something running **on the host** (not in another container). Examples:

- A database you installed locally without a container.
- An auth proxy (Keycloak, mitmproxy) listening on a port on your laptop.
- A third-party service you're mocking on the host.

On **Docker Desktop (Mac/Windows)**, the hostname `host.docker.internal` already resolves automatically to the host's gateway. Just use `http://host.docker.internal:PORT` in your code.

On **Linux native**, that hostname doesn't exist by default. To create the mapping (available since Docker Engine **20.10**), add this line to the service that needs it:

```yaml
services:
  backend:
    extra_hosts:
      - host.docker.internal:host-gateway   # creates the mapping on Linux
```

> **Not a stack standard.** This should NOT live in `docker-compose.yml` or `docker-compose.override.yml.example` by default. It's a tip for the specific case of crossing the container → host boundary. When you need it, declare it only on the specific service, ideally in your local `docker-compose.override.yml` (which is gitignored), and remove it once you're done.

**Common gotcha:** `host-gateway` resolves to the Docker bridge IP (typically `172.17.0.1` on Linux). For the container to actually connect, the host service must be bound to `0.0.0.0` (all interfaces), not only to `127.0.0.1`: otherwise the connection is refused. Something like `python -m http.server 8000` (which binds to `0.0.0.0` by default) works; a server bound to `127.0.0.1` (which several dev servers do by default) doesn't.

## 6. `docker-compose.yml` vs `docker-compose.override.yml`

Now that you know multi-stage, networks, and DNS, you can look at Compose without mystery. This is the central piece of the pattern.

> **Important:** we do not deploy to production with `docker compose up`. Production runs on Kubernetes, Swarm, ECS, or similar — orchestrators that provide HA, rolling deploys, scheduling, etc. The `docker-compose.yml` here is a **local mirror** of what goes to production: same network topology, same versioned images, same exposed ports. When you run `make prod-like`, you're validating "this stack behaves enough like prod to reproduce bugs and test integration" — you're not producing an actual deploy.

### `docker-compose.yml` — local simulation of the prod environment

The `docker-compose.yml` describes **what the stack looks like in production**: versioned images (pulled from a registry, not built locally), only public-facing ports, final commands, networks. No `build:`, no source-code bind mounts, no default credentials.

> **Hard rule:** **`image:` lives in `docker-compose.yml`; `build:` lives ONLY in `docker-compose.override.yml.example`.** This separation isn't a stylistic choice, it's consistency with the real lifecycle:
>
> - In prod, nobody builds on the server — the orchestrator pulls the image from the registry. So `docker-compose.yml` (which mirrors prod topology) **does not** declare `build:`.
> - In dev, you need to compile the code on your branch on every change. So `build:` (with `target: dev`) lives in the override, alongside bind mounts and debug ports.
> - When you run `docker compose build` (which auto-merges both files), Compose uses `image:` from the main file as the destination tag and `build:` from the override as the recipe. Result: the tag points to the image built at the `dev` target.
> - When you run `docker compose -f docker-compose.yml up`, the override is ignored and the existing image (cached locally or pulled from a registry) is used as-is. Same prod topology, no local build.
>
> This eliminates the "is this tag dev or prod?" ambiguity from day-to-day work: it is whatever the last `build`/`pull` put there. Because dev and prod share the tag, the `dev` stage must be **self-contained** (see §3): if the dev image is accidentally used by the prod compose, it still runs against the internal snapshot instead of crashing.

It serves two purposes:

1. **Locally, with `make prod-like`**, to reproduce the behavior that will run on the server (backend with no exposed port, pinned tags, etc.).
2. **As the single topology reference** for the DevOps team that translates this compose into Kubernetes/Swarm manifests/Helm chart. Whoever deploys has a single file to look at to understand what comes up, in what order, with which networks.

```yaml
services:
  frontend:
    image: ${DOCKER_REGISTRY:-localhost}/example/frontend:${PROJECT_TAG:-latest}
    env_file: .env
    environment:
      NEXT_PUBLIC_API_URL: http://bff:3000    # catraca DNS: no IP, no localhost
    ports:
      - "${FRONTEND_PORT:-3001}:3000"
    networks:
      - catraca

  bff:
    image: ${DOCKER_REGISTRY:-localhost}/example/bff:${PROJECT_TAG:-latest}
    env_file: .env
    environment:
      BACKEND_URL: http://backend:8080        # internal DNS
    ports:
      - "${BFF_PORT:-3000}:3000"
    networks:
      - internal
      - catraca

  backend:
    image: ${DOCKER_REGISTRY:-localhost}/example/backend:${PROJECT_TAG:-latest}
    env_file: .env
    environment:
      DATABASE_URL: mongodb://database:27017
    # NO `ports:` — backend is only reachable from inside catraca/internal
    networks:
      - internal
      - catraca

  database:
    image: mongo:7
    volumes:
      - database-data:/data/db
    networks:
      - internal

networks:
  internal:
  catraca:
    external: true
    name: catraca

volumes:
  database-data:
```

Patterns that repeat across all projects:

- **Parameterized image** via `${DOCKER_REGISTRY:-localhost}` and `${PROJECT_TAG:-latest}`. The same file works for simulating prod locally (no variables → falls back to `localhost`) and for feeding CI/CD pipelines that pull versioned images from the registry (`DOCKER_REGISTRY=registry.company PROJECT_TAG=v1.2.3 docker compose pull`).
- **Ports and configs with defaults** via `${VAR:-default}`. You can bring the stack up without any `.env` boilerplate.
- **No `build:`.** Mirrors the real scenario: in prod (Kubernetes/Swarm), nobody compiles on the server — they just pull images from the registry. Locally, `make prod-like` does the same.
- **Topology per section 4:** frontend and bff with `ports:`, backend and database without.

### `docker-compose.override.yml` — dev default

Compose automatically loads both files when you run `docker compose up`, merging them. The override is the **dev complement**: local build, hot reload, source-mounting volumes, debug ports.

```yaml
services:
  frontend:
    build:
      context: ./frontend
      dockerfile: .docker/build/Dockerfile
      target: dev
    volumes:
      - ./frontend:/app
      - /app/node_modules
      - /app/.next
    command: npm run dev

  bff:
    build:
      context: ./bff
      dockerfile: .docker/build/Dockerfile
      target: dev
    volumes:
      - ./bff:/app
      - /app/node_modules      # ← anonymous volume, see 9.6
    command: npm run start:dev

  backend:
    build:
      context: ./backend
      dockerfile: .docker/build/Dockerfile
      target: dev
    ports:
      - "${BACKEND_PORT:-8080}:8080"   # ← only in DEV: Postman, debugger, scripts
    volumes:
      - ./backend:/app
    command: air -c .air.toml

  database:
    # ports:                   # commented out: uncomment to connect with Compass locally
    #   - "${MONGO_PORT:-27017}:27017"
    environment:
      MONGO_INITDB_ROOT_USERNAME: ${MONGO_USER:-root}
      MONGO_INITDB_ROOT_PASSWORD: ${MONGO_PASS:-root}
```

In dev you can `curl http://localhost:8080/api/...` to hit the backend directly (handy for debug and Postman). In production, that simply doesn't exist. Traffic always enters through the frontend or the BFF.

### The detail most people miss: the `.example` pattern

The file **actually versioned** is not `docker-compose.override.yml`, but `docker-compose.override.yml.example`. The "real" override is a **local copy** of that template, created on the first `make setup` and listed in `.gitignore`:

```
docker-compose.override.yml.example   ← versioned (team template)
docker-compose.override.yml           ← ignored (developer's local copy)
```

This reproduces the same principle as `.env.sample` (versioned) vs `.env` (ignored); the `Makefile` handles **both** copies in the same `make setup`. The `.example` suffix follows a widely used community convention ([NetBox](https://github.com/netbox-community/netbox-docker/blob/release/docker-compose.override.yml.example), [PyPI Warehouse](https://github.com/pypi/warehouse), among others), so newcomers recognize it immediately. Benefits:

- **Single-command onboarding.** `make setup` copies the default and the developer has a functioning environment without editing anything.
- **The team updates the default without stepping on anyone's toes.** If someone adds a new service (e.g. a cache), it's a PR editing `.yml.example`. Anyone who wants to pull it updates via `make sync-override` (or deletes the local copy and runs `make setup` again).
- **Local freedom without endless `git stash`.** You can comment out `depends_on: database` because you run Mongo natively, change `mem_limit`, expose extra ports, swap `command`. Git never sees it, because the file is ignored.
- **Clean history.** No "tweak override" PRs polluting the log; only real infra changes, in `.yml.example`.

### Implementing it with a Makefile

A `Makefile` glues the whole flow together (create the network, copy `.env.sample` → `.env`, copy `.example` → local override, bring the stack up/down, debug per-service IPs, etc.). To avoid duplicating the file here, see the template in the example repo: [`example/Makefile`](./example/Makefile).

Main targets it exposes:

| Target               | What it does                                                       |
|----------------------|--------------------------------------------------------------------|
| `make setup`         | Creates the `catraca` network, copies `.env.sample → .env` and `.yml.example → .yml` |
| `make up`            | `docker compose up -d` with the override applied (dev mode)        |
| `make prod-like`     | `docker compose -f docker-compose.yml up -d` (ignores override)    |
| `make sync-override` | Updates the local override from `.example` (with backup)           |
| `make ip SVC=name`   | Shows the service IP on each network                               |
| `make ips`           | Lists IPs of all services                                          |
| `make logs SVC=...`  | Tails logs for one service                                         |
| `make sh SVC=...`    | Shell inside the container                                         |
| `make rebuild SVC=...` | `docker compose build --no-cache <svc>`                          |
| `make network`/`network-rm` | Idempotently create/remove the external network             |
| `make clean`         | `down -v --remove-orphans` (preserves the external network)        |
| `make reset-override` | Drops the local override to start over from the default           |

### Workflow in practice

```bash
# First time in the project:
git clone repo && cd repo
make setup                # copies .env.sample → .env  and  docker-compose.override.yml.example → docker-compose.override.yml
make up                   # brings up database, bff, and backend with hot reload

# Want to test as in production (backend without exposed port)?
make prod-like            # ignores the override, uses only docker-compose.yml

# The team updated the default (new service, new port)?
git pull
make diff-override        # see what changed
make sync-override        # adopt the new default (backs up your previous one)

# Want to start over?
make reset-override && make setup
```

### Summary

- `docker-compose.yml` is the **immutable contract**: it describes the topology going to prod (on the real orchestrator) and doubles as a local mirror. It doesn't change on a whim.
- `docker-compose.override.yml.example` is the **team template**: versioned, evolves via PR.
- `docker-compose.override.yml` is the **developer's playground**: gitignored, copied from the default, freely modified for each machine.
- The `Makefile` glues it all: `make setup` to start, `make sync-override` to track team changes, `make prod-like` to simulate prod locally.

### Why this matters

1. **Instant onboarding.** `git clone && make setup && make up` brings up a functional environment, no README required.
2. **Faithful prod simulation.** `make prod-like` ignores the override and brings up the stack as it looks in production (pinned images, backend without exposed port, no hot reload). Useful for reproducing environment-specific bugs without deploying.
3. **No `if NODE_ENV=development` conditionals in the Dockerfile.** The difference between dev and prod is declared in the orchestration (`target`, `command`, `volumes`, `ports`), where it belongs.
4. **Freedom without conflict.** Each developer can comment out `depends_on: database` (because they run Mongo natively), expose or hide ports, change image versions, without ever opening a PR for it, and without a dirty `git status`.

## 7. `.dockerignore`

Small but critical. The "build context" is everything in the folder you pass to `docker build .` (or that Compose passes implicitly). Docker ships that whole context to the daemon before starting, so trimming what doesn't matter is essential.

Typical examples:

| Project type      | `.dockerignore` content                              |
|-------------------|------------------------------------------------------|
| Frontend/BFF Node | `.docker`, `node_modules`, `.next`, `dist`, `.env*` |
| Backend Go        | `.docker`, `build`, `tmp`, `.data`, `.env*`         |
| Generic           | `.git`, `.vscode`, `.idea`, `coverage`, `*.log`     |

### Why it matters

1. **Build speed.** Without `.dockerignore`, the daemon receives `node_modules/` (hundreds of MB), `.next/`, dumps, volume data. Builds get slow and cache gets blown unnecessarily.
2. **Stable cache.** Any file change in the context invalidates layers. Ignoring `node_modules`, `tmp`, `dist` ensures `COPY . .` only fires when actual code changed.
3. **Security.** Without ignores, any `.env`, credentials, or local backups become part of the image. Even if unused at runtime, they leak through any `docker save` or registry leak.
4. **Consistency with `.docker/`.** Because all infrastructure lives in `.docker/` (including the Dockerfile itself), ignoring `.docker` in the build context avoids a silly loop: the Dockerfile being executed doesn't need to be inside the context it copies.
5. **Why ignore `.data/` and `.docker/data/`.** These directories are mounted as binds to persist database/cache locally; they can be gigabytes. They must never enter the build context.

> Practical note: `.dockerignore` follows rules similar to `.gitignore` but it's independent. A file can be committed to git and still be ignored by the build (typical case: `README.md`, `docs/`, dev-only `scripts/`).

---

## 8. `.gitignore`

`.gitignore` follows two principles:

1. **Ignore everything generated.** `dist/`, `build/`, `tmp/`, `node_modules/`, `.next/`, `coverage/`, `*.tsbuildinfo`, `next-env.d.ts`.
2. **Ignore everything local/sensitive.** `.env*`, `.idea/`, `.vscode/*` (with exceptions for team-shareable configs), `.DS_Store`, `*.swp`, `docker-compose.override.yml`.

### Specific points that became convention

- **`.env*` fully ignored**, with a versioned `.env.sample` serving as living documentation of the variables.
- **Compose data folders** (`.docker/data`, `.data/`) stay out: those are created at runtime by bind mounts.
- **`uploads/`** ignored in backends that accept dev uploads, to avoid accidental commits.
- **`vendor/` and `go.work`** ignored in Go projects: we prefer reproducible `go.mod`/`go.sum` over vendoring.
- **Selective IDE configs.** The pattern `.vscode/*` + `!.vscode/settings.json` lets you share team settings (suggested extensions, debugger configs) without committing personal preferences (everyone's own `launch.json`, etc.).

## 9. Other best practices

### 9.1. Defaults with `${VAR:-fallback}`

Anything configurable has a sensible default. This means `docker compose up` works "out of the box". Variables only add friction when there's a reason (`MONGO_ROOT_PASSWORD` with no default is justifiable; `APP_PORT` with no default is not).

### 9.2. `env_file: .env`

Instead of listing 30 variables on every service, Compose loads `.env` directly. Combined with `.env.sample`, it keeps setup short and secrets out of the repo.

### 9.3. Named volumes for data that must survive `down/up`

Named volumes (`database-data:/data/db`) are Docker-managed and survive `docker compose down`. Bind mounts (`./.docker/data/db:/data/db`) are for cases where the developer wants to inspect/export data via the host filesystem. Pick one or the other, not both on the same service at the same time.

### 9.4. `profiles:` for optional services

When a service only makes sense in some scenarios (a queue worker, an admin panel, a seed tool), use **profiles** instead of leaving it always running:

```yaml
services:
  worker:
    image: example/worker
    profiles: ["workers"]      # only starts if you pass --profile workers

  seed:
    image: example/seed
    profiles: ["tools"]        # same idea
```

Behavior:

- `docker compose up` → starts only services **without** `profiles:`.
- `docker compose up --profile workers` → starts the above + services with the `workers` profile.
- `docker compose --profile workers --profile tools up` → starts everything.

Advantages over the old `deploy.replicas: 0` trick: it's the official, idiomatic form in Compose v2+, guaranteed to work in all modern versions, and declarative. The team can see in the compose file which profiles exist without guessing.

### 9.5. Commented-out ports rather than removed

Common in `docker-compose.override.yml.example`:

```yaml
database:
  # ports:
  #   - "${MONGO_PORT:-27017}:27017"
```

The intent: by default, the database doesn't expose a port to the host (avoiding conflicts with a native Mongo); but if you need to connect via Compass, uncomment it in your local override. Documentation as code.

### 9.6. Hot reload without rebuild — and the anonymous `node_modules` trick

For Node (frontend, BFF), the formula that works is:

```yaml
volumes:
  - ./:/app                    # bind mount: host code appears inside the container
  - /app/node_modules          # ANONYMOUS volume: "preserves" the container's node_modules
```

#### What that line solves

Without the anonymous volume, here's what happens:

1. The Dockerfile's `deps` stage installs `node_modules` inside the container (Linux/glibc-alpine).
2. The override mounts `./:/app`, overwriting `/app` with the host's contents.
3. If the host has `node_modules` (from an `npm install` run outside Docker), it **replaces** the `node_modules` that was in the image, and probably breaks because it was compiled on macOS/Windows or with a different Node version.
4. If the host has **no** `node_modules`, you have no deps at all: `npm run dev` fails with `Cannot find module`.

Either way, the app doesn't start. The classic symptom is "works outside Docker but breaks with `docker compose up`", because native dependencies (`bcrypt`, `sharp`, `node-sass`, `argon2`, etc.) need to be compiled for the container's architecture.

#### How the anonymous volume fixes it

`- /app/node_modules` (with no `./` in front) creates a **Docker-managed anonymous volume** and mounts it at `/app/node_modules`. Because volumes take precedence over bind mounts on overlapping paths, the image's `node_modules` content is preserved inside the container, even with the rest of `/app` coming from the host.

Result:
- Host code → appears at `/app` (hot reload works: edit on the host, container sees it instantly).
- Image's `node_modules` → stays untouched at `/app/node_modules` (Linux/Alpine, properly compiled).
- Host's `node_modules` → doesn't get in the way (it doesn't even need to exist).

#### When to prefer a named volume over anonymous

Anonymous volumes have two drawbacks: (1) they're wiped by `docker compose down -v` along with "real" volumes, so next time you wait for the whole `npm ci` again; (2) they're hard to inspect (`docker volume ls` shows a hash, not a readable name). For projects where installation takes a while, swap for a **named volume**:

```yaml
services:
  bff:
    volumes:
      - ./:/app
      - bff_node_modules:/app/node_modules

volumes:
  bff_node_modules:
```

It survives `down/up` without `-v`, it's inspectable (`docker volume inspect project_bff_node_modules`), and you can clean it up explicitly when needed.

> Complementary (not a replacement): `RUN --mount=type=cache,target=/root/.npm npm ci` in the Dockerfile uses BuildKit to cache the **download** of packages (the tarball npm fetches before extracting) between builds. Speeds up the build, doesn't help at runtime. Combine it with the anonymous/named volume, don't swap one for the other.

#### Same technique for other folders

```yaml
volumes:
  - ./:/app
  - /app/node_modules          # Node
  - /app/.next                 # Next.js: local build cache from the image
  - /app/dist                  # when the container does incremental builds
  - /app/tmp                   # Go with Air
```

#### In Go with Air

The Go equivalent is simpler: since there's no `node_modules`, the bind mount `./:/app` is enough. But Air needs `/app/tmp` to write intermediate binaries, so it's worth protecting that directory with an anonymous volume too — otherwise the host fills up with `tmp/main` files spat out by the container.

### 9.7. Compose with an auxiliary file, and starting a single service

Observability stacks (Grafana, Tempo, Prometheus), admin panels, seed tools: all of these can live in a separate `docker-compose.observability.yml`, brought in via `docker compose -f docker-compose.yml -f docker-compose.observability.yml up`. The benefit: not every developer has to start Grafana + Tempo when they're only touching the API.

By default, `docker compose up` starts **all** declared services (combining files passed with `-f` and the automatic override). When you want only part of it:

```bash
docker compose up backend                       # only backend (and its depends_on dependencies)
docker compose up backend database              # backend + database, nothing else
docker compose up -d --no-deps bff              # only bff, without starting the backend declared in depends_on
docker compose up --build --force-recreate bff  # rebuild and recreate only bff
docker compose restart bff                      # restart without rebuilding
```

> **Known bug with `--no-deps` + `depends_on: condition: service_healthy`.** In some Compose v2 versions (issues [#9591](https://github.com/docker/compose/issues/9591), [#10759](https://github.com/docker/compose/issues/10759)), `--no-deps` can error out with "no such service" or unexpectedly recreate dependency containers when `depends_on` uses healthchecks. In dev, prefer starting the full stack normally and only use `--no-deps` in targeted scripts.

In the `Makefile`, you can shorten via `SVC=` (already in the `logs`, `rebuild`, `sh` targets). In projects with 5-10 services, starting them all eats RAM/CPU for nothing. Working "one piece at a time" keeps the dev loop light, especially on modest machines or when running two catraca projects at once.

### 9.8. Avoid `latest` — pin everything to an explicit version

`latest` is a silent anti-pattern. It compiles and seems to work, but it embeds three problems at once:

1. **Non-determinism.** The same `docker compose up` today and three months from now can pull different images (because someone republished `node:latest`, `mongo:latest`, etc.). Builds that "worked" start breaking with no code change.
2. **Hard to roll back.** When something breaks in production, you don't know which version was running. `docker image inspect` shows a digest, but you have to dig to find out which tag that digest belonged to. Rollback becomes archaeology.
3. **Deceptive cache.** Docker treats `node:latest` as "already downloaded" and doesn't update it, even if the registry has a newer version. On some hosts you're running what you pulled in January, on others what you pulled in May.

#### Where this shows up and how to fix it

**Base images in the Dockerfile.** Pin at least major+minor, ideally the patch too:

```dockerfile
# ❌ Bad
FROM node:latest
FROM golang:alpine
FROM mongo

# ✅ Good
FROM node:22.11-alpine
FROM golang:1.25.5-alpine
FROM mongo:7.0.14

# 🏆 Best: pin by digest (immutable)
FROM node:22.11-alpine@sha256:abcd1234...
```

Pinning by digest is the only fully reproducible form: a tag can be overwritten by the maintainer, a digest cannot. For critical projects it's worth the overhead; for dev, `major.minor-alpine` covers 90% of cases.

**Your own service images in compose.** The `${PROJECT_TAG:-latest}` pattern that appears in the `docker-compose.yml` examples is fine as a **fallback for local dev** (when nothing's set, you get the last build), but in production **always** pass an explicit tag:

```bash
# ❌ In production
docker compose pull && docker compose up -d

# ✅ In production
PROJECT_TAG=v1.42.0 docker compose pull && PROJECT_TAG=v1.42.0 docker compose up -d
# or via CI env:
PROJECT_TAG=$(git rev-parse --short HEAD) docker compose up -d
```

Common schemes for `PROJECT_TAG`:

- **Short Git SHA** (`a3f9c12`): simple, unique, easy to trace in CI logs.
- **SemVer** (`v1.42.0`): good for releases; combine with `git tag`.
- **Date + SHA** (`2026.05.22-a3f9c12`): sortable, instantly readable as the build date.

Avoid mutable semantic tags (`stable`, `prod`, `release`) for the same reason as `latest`: someone can rewrite where `stable` points.

> Simple rule: if your production image name contains `latest`, treat it as a bug. For local dev it's OK, but any CI/CD pipeline must always pass a deterministic tag.

**References to defend in a security review:** the [CIS Docker Benchmark](https://www.aquasec.com/cloud-native-academy/docker-container/docker-cis-benchmark/) explicitly recommends "always tag images with a specific version", and the [OWASP Docker Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Docker_Security_Cheat_Sheet.html) lists "Rule 8: Do not use the latest tag" among hardening practices.

### 9.9. Avoid `container_name:` — it unlocks `--scale`

Don't pin the container name in compose:

```yaml
# ❌ Bad
services:
  backend:
    container_name: backend
```

It looks harmless (and pretty in `docker ps`), but it breaks a powerful Compose feature: **scaling a service** (covered in detail in section 10). Because container names must be unique on the daemon, `docker compose up --scale backend=3` fails with `Conflict. The container name "/backend" is already in use`.

Without `container_name`, Compose auto-generates names with the pattern `<project>-<service>-<n>` (e.g. `myapp-backend-1`, `myapp-backend-2`).

#### When would `container_name` make sense?

Almost never. The legitimate cases are rare: integration with an external tool that needs a fixed hostname (e.g. a `docker exec` in old CI, a legacy monitoring script). Even then, **prefer `hostname:`** (which only affects the container's internal DNS, not its daemon-side name) or network aliases. `container_name` is the one option that kills `--scale`.

### 9.10. Healthchecks

`healthcheck:` teaches Docker how to know whether the container is actually ready to receive traffic, not just running. It's what unlocks `depends_on: condition: service_healthy`, which makes `bff` wait for `database` to accept connections before starting.

```yaml
services:
  database:
    image: mongo:7
    healthcheck:
      test: ["CMD", "mongosh", "--quiet", "--eval", "db.runCommand({ ping: 1 })"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 20s     # grace period before counting failures

  backend:
    depends_on:
      database:
        condition: service_healthy   # only starts after the healthcheck passes
```

Without that, `backend` starts alongside `database` and you get ~5 seconds of connection errors until Mongo finishes initializing. With a healthcheck, Compose waits for the status to flip to `healthy` before starting `backend`.

**Useful patterns:**

| Service     | Example `test:`                                            |
|-------------|------------------------------------------------------------|
| HTTP API    | `["CMD", "curl", "-fsS", "http://localhost:8080/health"]`  |
| Postgres    | `["CMD-SHELL", "pg_isready -U $$POSTGRES_USER"]`           |
| MongoDB     | `["CMD", "mongosh", "--quiet", "--eval", "db.runCommand({ ping: 1 })"]` |
| Redis       | `["CMD", "redis-cli", "ping"]`                             |

> `CMD-SHELL` interprets the string in a shell; `CMD` executes directly without a shell. Use `CMD-SHELL` when you need environment variables (`$$VAR` in compose) or pipes.

### 9.11. `logging:` driver — don't fill up the disk

By default, Docker uses the `json-file` driver with no rotation. In production, a chatty app can fill the host's disk in days. Limit it explicitly:

```yaml
services:
  bff:
    image: ...
    logging:
      driver: json-file
      options:
        max-size: "10m"      # each log file up to 10MB
        max-file: "3"        # keep 3 files (rotation)
```

Result: at most 30MB of logs per container, with rotation. In environments with aggregation (Loki, ELK), swap for the corresponding driver (`loki`, `gelf`, `fluentd`) and keep `json-file` as a local fallback only.

### 9.12. Resource limits

By default, a container can consume all of the host's memory/CPU. In dev that's rarely a problem; in production (or when running many catraca projects in parallel on your machine), it's worth limiting:

```yaml
services:
  backend:
    image: ...
    mem_limit: 512m          # kills the container if it exceeds 512MB
    cpus: 1.0                # at most 1 CPU
```

In Swarm/Kubernetes the equivalent syntax is `deploy.resources.limits.memory` / `deploy.resources.limits.cpus`. In non-Swarm Compose v2 both forms work, but the short form above is more readable and more portable across versions.

Mostly useful for:
- Ensuring a memory leak kills the container instead of the whole laptop.
- Reproducing prod limits locally (if prod backend has 512MB, running with 512MB in dev surfaces leaks early).
- Running several catraca stacks side by side without insane swap.

## 10. Scaling services with `--scale`

When the anti-patterns from section 9 are out of the way (no `container_name`, no mandatory fixed ports), Compose hands you a free superpower: running multiple replicas of the same service with a single command.

### 10.1. How it works

```bash
docker compose up -d --scale backend=3
# creates:
#   project-backend-1
#   project-backend-2
#   project-backend-3
```

And the internal DNS **automatically load-balances**: other containers calling `http://backend:8080` receive round-robin among the three replicas. No load balancer required, no config change — as long as you've followed the requirements in the next sections.

### 10.2. Port ranges (fixed ports also break `--scale`)

If the service exposes a fixed port to the host (`8080:8080`), `--scale` fails for the same reason as `container_name`: host ports are unique, and two replicas would try to bind the same one. To unlock it, declare a **range** on the host side:

```yaml
services:
  backend:
    ports:
      - "8080-8089:8080"     # host: range of 10 ports | container: fixed port
```

Now `docker compose up --scale backend=5` distributes replicas across `8080`, `8081`, `8082`, `8083`, `8084` automatically, each one listening on `8080` internally. Whoever hits internal DNS (`http://backend:8080`) keeps using the internal port; whoever comes from outside (`localhost:8081`) hits one specific replica via the host.

Useful variations:

```yaml
ports:
  - "8080"                       # only internal port — Docker picks an ephemeral host port per replica
  - "127.0.0.1:8080-8089:8080"   # range bound to loopback only (not exposed on the machine's network)
```

> **Rule of thumb:** every exposed port on a scalable service should have a range on the host side (or be omitted). Fixed ports only make sense on singletons (BFF, gateway).

### 10.3. Debug ports

Debug ports also conflict with `--scale` if they're fixed. Since they only make sense in dev, they live in `docker-compose.override.yml.example`:

```yaml
services:
  bff:
    ports:
      - "8080-8089:8080"      # app
      - "9229-9238:9229"      # Node --inspect (10 slots to scale up to 10 replicas)
    command: node --inspect=0.0.0.0:9229 dist/main.js

  backend:
    ports:
      - "8090-8099:8080"      # app
      - "2345-2354:2345"      # Delve (Go)
```

Debug ports by language:

| Language         | Default port | Flag                                            |
|------------------|--------------|-------------------------------------------------|
| Node.js          | `9229`       | `node --inspect=0.0.0.0:9229`                   |
| Go (Delve)       | `2345`       | `dlv --listen=:2345 --headless --api-version=2` |
| Java JDWP        | `5005`       | `-agentlib:jdwp=...,address=*:5005`             |
| Python (debugpy) | `5678`       | `python -m debugpy --listen 0.0.0.0:5678`       |

Without the range, debugging one of several replicas in VS Code/IntelliJ becomes a lottery: you don't know which instance the breakpoint will hit. With the range, each replica lands in a predictable slot and you can configure multiple "launch configurations" pointing at `localhost:9229`, `localhost:9230`, etc.

### 10.4. DNS round-robin and the keep-alive gotcha

Round-robin happens on each **new DNS resolution**, not on each request. Modern HTTP clients (`http.Agent` in Node, default `http.Client` in Go, persistent connections from DB drivers) cache the resolved IP and reuse the TCP connection, so a single instance can receive 100% of the traffic even when there are 3 replicas.

For realistic load tests:

- **Option 1:** disable keep-alive on the client (`new http.Agent({ keepAlive: false })` in Node; `Transport.DisableKeepAlives = true` in Go).
- **Option 2:** put an L7 proxy (Traefik, nginx, HAProxy) in the middle that balances per request, not per connection.
- **Option 3:** run the load client (k6, wrk) with short connections (`--connections 100 --duration 30s --keepalive=false`).

Without one of those, your "5-replica load test" might actually be hammering a single instance.

### 10.5. Imperative (`--scale`) vs declarative (`deploy.replicas`)

Two ways to bring up multiple replicas in Compose v2:

**Imperative — `--scale` on the command line:**

```bash
docker compose up -d --scale backend=3
```

Good for ad-hoc experiments, local load testing, quick debugging. The number isn't versioned anywhere, so next time you have to remember to pass `--scale` again.

**Declarative — `deploy.replicas:` in compose:**

```yaml
services:
  backend:
    image: example/backend:${PROJECT_TAG:-latest}
    deploy:
      replicas: 3            # always brings up 3 replicas on `docker compose up`
      restart_policy:
        condition: on-failure
        max_attempts: 3
    ports:
      - "8080-8089:8080"
```

Here the number is in git and any `docker compose up` (without `--scale`) brings up 3 replicas. Good for services where the count is part of the contract (workers, queue schedulers, stateless backends).

> **Historical note.** `deploy:` originally was Swarm-only. In modern Compose v2, `deploy.replicas` and `deploy.restart_policy` **are honored by ordinary `docker compose up`**, not just by `docker stack deploy`. Other `deploy:` keys (`mode: global`, `placement:`, `update_config:`) still only make sense in Swarm/Kubernetes.

You can combine the two: declare `replicas: 3` as default and override with `--scale backend=10` when you want an ad-hoc load test.

### 10.6. Use cases

- **Local load test.** `docker compose up --scale backend=10` simulates concurrency without standing up Kubernetes/Swarm. Combine with `wrk`, `vegeta`, or `k6` pointed at the BFF and measure real throughput with multiple backend instances (mind the keep-alive gotcha from section 10.4).
- **Race-condition debugging.** Bugs that only show up under multiple instances (badly shared cache, broken distributed lock, broken idempotency) become reproducible locally.
- **Stateless validation.** If your app doesn't run under `--scale > 1`, it's got hidden in-memory state. Better to find out now than in production.
- **Workers and jobs.** For queue-processing services, `--scale worker=5` (or `deploy.replicas: 5`) is the trivial way to parallelize.

## 11. Rules summary

| Rule | Why |
|------|-----|
| Single `.docker/build/Dockerfile`, multi-stage | One file serves dev + prod, with cache reused across stages |
| `docker-compose.yml` = production (no `build:`, `ports:` only for public services) | Faithful mirror of what runs on the server; backend stays invisible |
| Versioned `docker-compose.override.yml.example` + ignored local `.override.yml` | Devs edit freely without merge conflicts; `make setup` clones the default |
| BFF as the only public entry; backend without `ports:` in prod, exposed only in the override | Reduces attack surface; in dev you still get direct access for debug |
| Two networks: `internal` per project + external `catraca` | Database isolated; apps see each other across repos via Docker's DNS |
| Services call each other by **name via internal DNS** (`http://backend:8080`), never via `localhost` | Stable config between dev/prod; no hard-coded IPs; `localhost` is the container's own loopback |
| `host.docker.internal` is a situational tip, **not** a compose standard | Adding `extra_hosts` to every service pollutes YAML and implies a non-existent dependency |
| Idempotent `make network` as a prerequisite for `setup`/`up` | Ensures the external network exists before compose, no "network not found" error |
| Anonymous volumes for `node_modules`/`.next`/`tmp` in the override | Hot reload without the host's `npm install` breaking the image |
| `.dockerignore` trims `node_modules`, `.docker`, `.next`, data dirs | Faster builds, stable cache, no leaked secrets |
| `.gitignore` ignores artifacts + secrets + `docker-compose.override.yml` | Clean repo; nothing generated lands; secrets never leak |
| `${VAR:-default}` on everything configurable | `up` works out-of-the-box; secrets require an explicit `.env` |
| Final image non-root, `scratch`/`distroless`/`standalone` | Smaller attack surface, smaller footprint |
| No `latest`: pinned tags (`node:22.11-alpine`, `PROJECT_TAG=<sha>`) in prod | Deterministic builds, traceable rollback, no silent update surprise |
| No `container_name:` — let Compose generate unique names | Unlocks `docker compose up --scale backend=N` for load testing and multiple replicas |
| Port ranges (`8080-8089:8080`) on scalable services | Each replica gets a unique host port; fixed ports only for singletons |
| `profiles:` for optional services | Idiomatic and correct replacement for `deploy.replicas: 0` |
| `healthcheck:` + `depends_on: condition: service_healthy` | Backend only starts after the database accepts connections |
| `logging:` with `max-size`/`max-file` | Doesn't fill the disk in production |
| `mem_limit:` and `cpus:` on long-running services | A leak kills the container, not the host |

## 12. Checklist for a new project

When creating a repository following this pattern:

- [ ] Create the `.docker/build/Dockerfile` structure as multi-stage with at least `deps → dev → builder → runner`.
- [ ] Write `docker-compose.yml` with parameterized images, no `build:`, `ports:` only for what's public in production.
- [ ] Write `docker-compose.override.yml.example` with `build:`, `target: dev`, source bind mounts, anonymous volumes for dependencies, and backend debug ports.
- [ ] Declare the `internal` (project-scoped) and `catraca` (`external: true, name: catraca`) networks in compose.
- [ ] Add `docker-compose.override.yml` and `*.bak.*` to `.gitignore`.
- [ ] Copy the `Makefile` from this directory to the project root.
- [ ] Create `.env.sample` with all variables used.
- [ ] Create `.dockerignore` trimming `node_modules`/`.docker`/`.next`/`build`/`.data`.
- [ ] Add `healthcheck:` to `database` and `depends_on: condition: service_healthy` to services that depend on it.
- [ ] Add `logging:` with `max-size`/`max-file` on every service heading to prod.
- [ ] Tag optional services (workers, seeds, admin panels) with `profiles:`.
- [ ] Validate with `make setup && make up` that the stack starts cleanly from a fresh clone.
- [ ] Validate with `make prod-like` that the production version also starts (without the backend port exposed).
- [ ] If scalable, validate with `docker compose up --scale backend=3` (no `container_name:`, with a port range).
